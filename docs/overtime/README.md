# 業務假日或臨時加班登記 · V1.1.9

GitHub Pages 前端：`https://sianyu030.github.io/order_web/overtime/`。原報修首頁不變。

## 正式流程

1. 業務選擇日期、E5 業務人員、加班時數及原因。
2. 送出後僅把申請記錄寫入同份試算表的**隱藏來源分頁**「業務假日或臨時加班登記」（gid 1399193095），狀態「待核准」，絕對不從申請送出路徑寫 E5 月表。
3. Google 試算表「業務加班月檢視」（gid 2131065558）根據來源分頁過濾選定年／月，顯示日期、姓名、時數、原因、狀態及「主管核准」連結；ID 放在隱藏 F 欄，排序後連結仍與該筆申請同列。
4. 主管透過連結 `?approve=BUS-yyyymmdd-E5-id` 進入 GitHub Pages 審核頁，需以 OAuth 登入。系統核對申請狀態與真正年份、月份、E5 業務工號、姓名、目的欄位及是否已有加班時數。
5. 主管確認之後，才用 Sheets API 寫入原本 E5 月表的**加班時數及同格 Google「註解」**。讀回雙重確認後，來源分頁 P 欄才標示「已核准」，Q/R 紀錄主管 email 和時間。註解採 2026-09-30 正式開放的 Sheets comments API。
6. 其他單位、班別、支援、請假、便當公式皆不更動。原表有加班資料時不會直接覆蓋。

## 實際限制，請勿把展示版本當成正式環境

- **已完成且可驗證**：Google Sheets 月檢視新增狀態／核准連結；網站程式分離待核准申請與 E5 寫入；員工名冊僅開放主檔中 `單位=內勤` 且 `細分區域=業務` 的 6 位在職業務；基本 JS 語法與純邏輯測試。
- **尚未完成**：公司 OAuth Client ID、主管 email 授權清單、可信任的後端權限控管、實際授權登入／時數及註解回寫測試。
- `APPROVER_EMAILS = []` 是**刻意保留的核准安全鎖**。由於主管 email 尚未取得，正式核准按鈕保持停用。不可以為了演示而猜測主管帳號或把白名單設為所有人。
- 單靠 GitHub Pages 前端 email 白名單**不是安全的授權邊界**；有 Google Sheets 編輯權限的人可繞過網站直接改試算表。正式多人使用應由具有伺服器端身份驗證／權限控制的後端執行核准寫入，且不可把服務帳號祕鑰放到公開程式庫。Google Apps Script 可作後端，網站仍維持 GitHub Pages，但現階段尚未配置。
- 網站仍為展示模式時，資料只保存在本機瀏覽器，**不會跨裝置顯示在月檢視**。
- 若核准時時數成功、註解失敗，程式顯示部分成功並阻止標記已核准，需人工核對後處理。未測過此情況的真實 Google 帳號環境。

## Google 授權需求

- Google Cloud 啟用 Google Sheets API，建立 OAuth Web Client，授權 JavaScript origin `https://sianyu030.github.io`。
- 網頁目前使用 `openid email https://www.googleapis.com/auth/spreadsheets` 授權範圍。
- 切勿貼 Google 密碼、OAuth Client Secret、服務帳戶 JSON 到網頁或 GitHub。

## V1.1.1：防止漏登、重複寫入

- 申請來源固定使用原本 `A2:R1500` 空白列，以 `updateCells` 精準定位；不再 `appendCells` 到表格資料尾端而超出月檢視範圍。
- 同日期／同工號的待核准申請使用同一筆 ID；未修改的內容不重複寫入，已核准申請禁止被業務修改。
- 限制只有在職 E5 業務對應的工號可以送出；超過容量會阻止寫入並明確顯示錯誤。
- 使用虛構測試資料對「建立、更新、無異動、滿表防護、核准後不可改、只寫來源分頁」跑過程式測試。
- **真正 Google OAuth 登入、多人同時送出、主管授權與寫入 E5／註解尚未完成端到端實測。** `APPROVER_EMAILS=[]` 仍刻意維持禁止正式核准。前端白名單不足以構成正式身分權限；需要可信任的後端。

## V1.1.2：加入正式業務姓名預覽和 E4 指定人員

- E5 登記員工共 6 位，E4 僅指定「潘詠升」可選。名單依已連線的人員主檔「內勤／業務／在職」及「E4／E4櫃體股／在職」核對。
- 未登入 Google 時只預覽**姓名與單位**，選單使用合成識別碼 PREVIEWxx，不得當作正式工號，亦無法跨裝置送出申請。**注意：公開 GitHub 網站及程式碼可以看見這七位姓名，務必先確認公司政策是否允許公開名單。**
- 登入後從原試算表安全取得並使用完整工號，並依姓名承接先前預覽選擇；所有正式送出必須重新核對主檔。
- E4 審核定位使用對應 `M月份E4`，E5 仍使用 `M月份E5機修課`，不得混寫；修改紀錄的唯一 ID 帶入 E4/E5 單位。
- 模擬測試：7 位姓名預覽、只開放 E4 指定人員、E4 11/16 月表儲存格定位、建立／更新／無異動／核准後鎖定、所有送出先存待核准分頁。
- 主管授權名單仍為空，正式核准禁用。OAuth 未完成，未執行真實員工加班時數或註解寫入驗收。

## V1.1.4：主管多筆核准寫入及駁回刪除

- 網站新增「主管批次」分頁，提供待核准清單、全選／單選、核准並寫入與駁回刪除按鈕。支援手機與電腦。
- 主管核准多筆時逐筆處理，每筆重新比對原人員主檔 E4／E5、日期、原月表儲存格、既有值與註解。時數與 Google 試算表同格留言讀回都確認成功後，才將該筆狀態寫成「已核准」；遇到錯誤立即停止剩餘申請，明確告知已完成筆數。
- 駁回刪除是**從待核准畫面和月檢視移除**，來源紀錄仍保留為「已駁回」，不刪除真正 E4／E5 工時。可在來源表查看駁回者與駁回時間。
- 駁回後可重新申請，同日相同人員使用獨立尾碼 `-R1`、`-R2`，避免覆蓋原駁回紀錄。待核准申請的修改仍保持單一當前有效 ID。
- Google Sheet「業務加班月檢視」G2 加入批次處理入口，A5 的篩選公式排除「已駁回」；來源表 P 欄下拉新增「已駁回」。
- 安全：尚未取得授權主管的 Google 帳號及可信任伺服器端核准機制，`APPROVER_EMAILS=[]` 故**真實核准與駁回保持鎖定**。單靠公開 GitHub Pages 前端白名單並不具備真正安全權限隔離，不能將名單設為任意使用者或直接交付正式環境。
- 單筆與批次均經程式語法和模擬 API 測試：2 筆分別 E4/E5 核准、留言與時數檢查、駁回未變動月表、重複核准禁止、已有公式禁止覆寫、留言部分失敗保持待核准、駁回後重新申請與唯一 ID。
- **尚未實際操作公司 Google OAuth／正式員工工時／真實 Google Sheets 留言。** 避免以真實工時進行冒險測試。要正式啟用仍需配置安全後端、主管認證並用明確授權的測試資料做端到端驗收。

## V1.1.5：Google 月檢視與網站都可以開啟核准／駁回

- Google 試算表「業務加班月檢視」保留 G 欄「主管核准」單筆連結，另新增 K 欄「駁回刪除」單筆連結。H:J 是原本隱藏的日期／假日公式參考欄，保留不更動。G2 上方保留「主管批次核准／駁回」入口。

- 網站的「主管批次」仍可單選／全選多筆核准或駁回。來源分頁保留已駁回及核准稽核紀錄；核准前不寫入 E4／E5 工時。

- 月檢視仍按 B2 年、D2 月、B3 日篩選，選「全部」才會顯示整個月份；當來源無登記時，動態連結列維持空白。

## V1.1.9：主管帳號後端已建立

- Supabase 專案 `rightway-overtime-approvals`（Tokyo 區域，建置時已確認每月報價 0 元）。
- Edge Function `overtime-auth` 具備獨立帳密核對、PBKDF2-SHA256 加鹽雜湊（210,000 次）、連續登入失敗鎖定 15 分鐘、8 小時工作階段、強制首次改密碼、帳號新增／啟停／重設及操作紀錄。
- 初始帳號 `3109` 是管理員，`1494` 與 `kurt` 是主管；主管初始密碼由管理者指定，所有初始帳號均標記 `must_change`。
- 主管入口在網站「主管批次」及試算表逐筆核准／駁回連結開啟時顯示；修改密碼與新增帳號不用再修改 GitHub 前端。
- 主管登入只能驗證身分，不代表已有 Google Sheet 寫入權限。**正式工時核准仍需 Google Sheets OAuth 及實際端到端驗收；任何授權未完成的動作必須保持拒絕寫入。**
- 目前後端存放的是主管密碼雜湊及權限，沒有把密碼、服務金鑰或真正員工工時寫進公開 GitHub。
